The problem

The count was the number — and the number moved.

On the floor, the morning inventory of dough compound and packaging film was a paper walk: eyeball a half-full tub, tally it, add it up on a calculator, type it into a spreadsheet. The plant's tracking system existed, but line-side moves weren't scanned reliably — so the planner rebuilt inventory by hand every morning and fed that hand-built number straight into supplier orders.

The deeper issue wasn't speed. It was that two trained people walking the same floor got two different totals — and a supplier order was riding on it.

Before

  • 2+ hours of manual counting, daily
  • Partial tubs estimated by eye
  • Tally → calculator → spreadsheet, by hand
  • No two counters agreed
  • System data distrusted, so ignored

After

  • A guided walk path, tap by tap
  • Enter tubs or kg straight off the tag
  • Totals and conversions computed live
  • System-vs-actual, with a tolerance band
  • Exceptions surfaced for the floor to fix

The solution

Everything the count needs, on one screen you can screenshot.

🧭

Guided walk path

Prompts the next area or machine in the exact order you walk the floor. One button completes a stop and advances; go out of order and it still tracks what's done.

⚖

System vs. actual

Your count against what the system expected, per location and material. Small gaps stay quiet; real ones — the tolerance band — turn to attention.

📊

Days of stock, with inbound

On-hand ÷ demand, then the honest version: what's inbound, its ETA, and days-of-stock after receipt. A low number with a truck arriving reads differently than one with nothing coming.

🚚

Transit → receiving

Load the carrier feed; planned trailers count as inbound, never as on-hand. Type a trailer or BOL and its whole contents post to the count in one tap — no double-counting.

⚑

Discrepancies that remember

Found-not-in-system, missing, and quantity-off items export for the floor team — and persist across days, so a location that keeps going unscanned shows exactly how long it's been flagged.

📊

Feeds the variance model

One tap exports a planning CSV that drops into a companion workbook, turning the day's count into supplier and std-weight variance — the numbers that drive ordering.

Config-driven by design. Materials, standards, rack bins, machines, the walk order, demand, and tolerances all live in one JSON block. Point it at a different plant — or a different industry — and the same code runs. The demo you can open is that exact mechanism, fed a fictional factory. Counts leave as CSV and feed a variance workbook, so the math stays visible and auditable instead of buried in the app.
How it was built

Shipped in the field, one real problem at a time.

Built as the working planner using it, so every feature answered a real friction on the floor — not a spec written in advance. The order below is the order it actually happened.

Watch the real count

Time it, map the walk, learn why the system data was distrusted. Design the data model before a line of UI.

Replace the paper

Tile-based counts by machine, rack validation against system data, live unit conversion — the core loop first.

Follow the floor

Encode the actual walk path so the tool self-prompts each stop in the order you physically move.

Turn counting into control

System-vs-actual with a tolerance band, plus days-of-stock against demand — so the count drives decisions, not just totals.

Close the loop

Correction sheets and a critical list the floor and planning teams act on — the count now feeds the whole workflow.
