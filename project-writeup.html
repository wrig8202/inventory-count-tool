Project write-up · Operations & data

I replaced a two-hour paper count with a system that tells me what to worry about.

A shop-floor inventory count was the number the whole supply chain trusted — rebuilt by hand every morning, and never twice the same. Here's how I turned it into an offline counting app and a variance model, and what changed as a result.

Olivia N. Wright · Operations & data · Built with AI-assisted development
Situation

The count was the number — and the number moved.

Every morning, two material families were inventoried by walking the floor with a printed sheet: eyeball a partial container, tally it, add it up on a calculator, type it into a spreadsheet. It took roughly two hours, spanned the shift change, and happened while trucks were unloading and material was moving to the lines. So the "count" wasn't a point-in-time snapshot — it was a moving observation stitched together across two and a half hours.

The plant's tracking system existed, but line-side moves weren't scanned reliably, so the planner distrusted it and rebuilt inventory by hand instead. That hand-built number then fed supplier orders directly.

The real problem wasn't speed. It was that two trained people could walk the same floor and get two different totals — and a supplier order was riding on it.
Task

Make the count reproducible, then make it decide something.

I set two goals, in order. First, stabilize: give the count a defined method so it stops depending on who's holding the clipboard. Second, make it useful beyond a total — connect on-hand to demand and inbound so the morning number answers the question that actually matters: am I going to run out, and if so, of what?

Constraints shaped everything. It had to run on a plant tablet with no network and no install, survive a browser with no IT footprint, and keep every calculation visible — because these numbers become supplier conversations, and a black box doesn't earn that kind of trust.

Action

An offline counting app, then a variance model on top of it.

I built a single-file, offline, config-driven counting tool — one HTML file, zero dependencies, no build step, that runs from a tablet's file browser. Everything specific to a plant (materials, standards, storage bins, machines, the physical walk order, demand, tolerances) lives in one config block, so the same engine can point at a different site or a different industry without touching the code.

What it does on the floor

  • Guides the walk. It prompts the next area or machine in the exact order you move through the building; one button completes a stop and advances, and it still tracks progress when you go out of order.
  • Shows what's expected. At each machine it surfaces the materials the system says should be there, so you're confirming against reality instead of hunting.
  • Separates signal from noise. System-vs-actual is shown per location with a tolerance band: differences within normal counting variance stay quiet; anything larger — almost always an unscanned move — is flagged.
  • Reads days of stock honestly. On-hand ÷ demand, then the version that matters: what's inbound, its ETA, and coverage after receipt. A low number with a truck two hours out is a different problem than a low number with nothing coming.
  • Links transit to receiving. Planned trailers count as inbound, never as on-hand. Type a trailer or BOL and its whole contents post to the count in one tap — and drop out of inbound so nothing is double-counted.
  • Remembers problems. Recurring discrepancies persist across days, so a location that keeps going unscanned shows exactly how long it's been flagged — the evidence you need to fix a process instead of counting around it.

What it feeds

The app doesn't try to be the system of record for the math. It exports a clean CSV that drops into a companion planning workbook, which turns the day's count — plus the carrier feed and the ordering system — into two views of variance: how suppliers are performing against what was promised, and whether received loads match their standard weights. That division of labor is deliberate: the app owns the floor, the workbook owns the math, and the seam between them is a CSV, which keeps the app offline and every calculation auditable.

A repeatable count that now drives decisions.

The count became reproducible. A defined method and a guided walk mean the total no longer depends on who counted, and differences from the system now carry a reason instead of a shrug.

The morning number now answers a question. Instead of a static total, it shows what's at risk after inbound is accounted for — the difference between reacting to a stockout and preventing one.

Discrepancies became evidence. Because problems persist across days, "the system is wrong" turned into "this location has been unscanned for six of the last eight days" — which is what actually moves a process fix.

And the whole thing stayed transparent. Keeping the math in a visible workbook rather than a black-box app is what lets the numbers stand up in a supplier conversation.

On method: the biggest lesson wasn't technical. It was stabilize before you optimize — understand what the count was really for, and why the workaround existed, before automating anything. Every feature answered a real friction on the floor, in the order it actually came up, because I was the one using it.
Insightful by design. Impactful by intention.
